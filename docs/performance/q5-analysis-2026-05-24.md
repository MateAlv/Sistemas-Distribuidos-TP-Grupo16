# Analisis de performance Q5

Fecha: 2026-05-24  
Rama de trabajo: performance test / improvement  
Dataset principal observado: `LI-Small`  
Objetivo: encontrar empiricamente el cuello de botella del flujo Q5 usando RabbitMQ UI, Docker Desktop y logs.

## Contexto

Q5 ya funciona end-to-end y pasa validacion funcional. El foco de este analisis no es corregir el resultado, sino entender por que el sistema tarda mucho con `LI-Small`.

El flujo relevante para Q5 es:

```text
file_ingestor
  -> transaction_fanout_exchange
  -> filter_q5_format_queue
  -> filter_q5_usd_queue
  -> aggregation_q5
  -> join_q5
  -> gateway/client
```

Durante las pruebas tambien corre el pipeline general, por lo que otras colas reciben el mismo fanout:

```text
filter_usd_queue
filter_q3_queue
filter_date_queue
scatter_gather_mapper_queue
sum_q2_queue
...
```

Esto es importante: el problema observado no parece ser solo de Q5, sino del costo de fanout y drenado de varias colas intermedias.

## Como leer RabbitMQ UI

Columnas principales:

- `Ready`: mensajes esperando en la cola.
- `Unacked`: mensajes entregados a consumidores pero todavia no confirmados.
- `incoming`: tasa de mensajes que entran a la cola.
- `deliver / get`: tasa de mensajes entregados a consumidores.
- `ack`: tasa de confirmaciones de consumidores.
- `Consumers`: cantidad de procesos consumiendo de esa cola.
- `Consumer capacity`: cuanto margen percibe RabbitMQ para entregar mensajes al consumidor. Si es bajo con mucho `Ready`, el consumidor o su patron de ack esta limitando el drenado.
- `Prefetch count`: cantidad maxima de mensajes sin ack que RabbitMQ puede entregar a cada consumidor.
- `Paged out`: mensajes sacados de memoria y paginados a disco por backlog/presion de memoria.

Regla rapida:

```text
incoming > ack durante mucho tiempo => backlog creciente
Ready creciendo => consumidor insuficiente o cuello posterior
Unacked ~= prefetch * consumers => los consumidores tienen su ventana llena
Paged out alto => RabbitMQ ya esta pagando costo de disco
```

## Observacion inicial: el sistema completo acumula backlog

En una corrida con `LI-Small` y configuracion base se observaron colas con millones de mensajes.

Ejemplo de `filter_q5_format_queue`:

```text
Ready: ~5.3M a ~5.9M
Unacked: 1
Consumers: 1
Prefetch count: 1
deliver/ack: ~2.4k/s
Consumer capacity: ~8%
Paged out: ~5.9M mensajes
Message body bytes: ~1.1 GiB
```

Ejemplo de `filter_usd_queue`:

```text
Ready: ~5.4M a ~5.9M
Unacked: 1
Consumers: 1
Prefetch count: 1
deliver/ack: ~3.5k/s
Consumer capacity: ~5%
Paged out: ~5.9M mensajes
Message body bytes: ~1.1 GiB
```

Interpretacion:

- El backlog no aparece solo en Q5.
- Varias colas del fanout reciben mas de lo que pueden drenar.
- Con `prefetch=1`, cada consumidor procesa estrictamente de a un mensaje: recibir, procesar, publicar salida, ack.
- Cuando el backlog llega a millones, RabbitMQ pagina casi todo a disco. Esa corrida queda contaminada para medir porque despues drenar implica leer desde disco.

## Docker Desktop: indicios de broker-bound

En una corrida base se observo aproximadamente:

```text
CPU total containers: ~400% a ~415% / 800%
rabbitmq: ~198% CPU
file_ingestor_0: ~103% CPU
filter_q5_format_0: ~39% CPU
filter_q5_usd_0: ~3.7% CPU
rates_service: 0%
```

Interpretacion:

- `file_ingestor` publica fuerte.
- `rabbitmq` consume mucha CPU moviendo mensajes.
- `filter_q5_usd` casi no trabaja, porque le llega poco trafico filtrado.
- `rates_service` no es cuello de botella en estas corridas.

Conclusion de esta etapa:

```text
El cuello esta antes de filter_q5_usd.
La conversion de tasas no domina todavia.
El problema principal parece ser fanout + colas intermedias + ack por mensaje.
```

## Experimento 1: escalar workers sin cambiar prefetch

Comando observado:

```bash
Q5_DATASET=LI-Small Q5_FORMAT_WORKERS=4 USD_WORKERS=4 KEEP_CONTAINERS=1 make test-q5
```

Resultado en `filter_q5_format_queue`:

```text
Consumers: 4
Unacked: 4
Ready: ~4.1M a ~4.9M
incoming: ~23.5k/s a ~25.9k/s
deliver/ack: ~2.3k/s a ~2.5k/s
Consumer capacity: ~11%
```

Docker Desktop mostro aproximadamente:

```text
CPU total containers: ~624% / 800%
rabbitmq: ~266% CPU
file_ingestor_0: ~60% CPU
filter_q5_format workers: ~12% cada uno
filter_usd workers: ~13% aprox
rates_service: 0%
```

Interpretacion:

- Pasar de 1 a 4 consumidores no dio mejora lineal.
- `deliver/ack` siguio cerca de ~2.5k/s.
- Los workers no estaban saturados individualmente.
- RabbitMQ si estaba muy cargado.

Conclusion:

```text
Agregar workers con prefetch=1 no alcanza.
El limite no parece ser CPU pura de filter_q5_format.
```

## Experimento 2: subir prefetch a 50 con 1 worker

Comando observado:

```bash
Q5_DATASET=LI-Small PREFETCH_COUNT=50 KEEP_CONTAINERS=1 make test-q5
```

Resultado en `filter_q5_format_queue`:

```text
Consumers: 1
Prefetch count: 50
Unacked: 50
Ready: ~2.5M a ~2.6M
incoming: ~10.2k/s a ~10.6k/s
deliver/ack: ~4.2k/s a ~4.5k/s
Consumer capacity: ~25%
```

Comparacion directa:

```text
prefetch=1, 1 worker  -> ~2.4k/s ack
prefetch=50, 1 worker -> ~4.2k/s a ~4.5k/s ack
```

Interpretacion:

- El aumento de prefetch casi duplico el throughput del consumidor.
- Esto confirma que `prefetch=1` era parte del cuello.
- Aun asi, `incoming` sigue siendo mayor que `ack`, por lo que la cola sigue creciendo.

Tambien se observo que `filter_q5_usd_queue` empezo a acumular un poco:

```text
Ready: ~4k
incoming: ~771/s
deliver/ack: ~518/s
```

Interpretacion:

- Al mejorar `filter_q5_format`, empieza a llegar mas carga a `filter_q5_usd`.
- Todavia no es el cuello principal, pero puede ser el siguiente cuando Q5 format drene mejor.

Conclusion:

```text
Prefetch mejora de forma real.
El siguiente experimento debe combinar mas workers + prefetch alto.
```

## Hipotesis actual

La hipotesis mas fuerte hasta ahora:

```text
El sistema esta broker-bound / fanout-bound.
```

Mas concretamente:

```text
file_ingestor publica muy rapido
transaction_fanout_exchange duplica cada transaccion hacia varias colas
varias colas tienen consumidores lentos o ventanas chicas
RabbitMQ acumula millones de mensajes
RabbitMQ pagina mensajes a disco
deliver/ack queda limitado por broker + ack/publish por mensaje
```

Esto explica por que:

- `rates_service` no consume CPU.
- `filter_q5_usd` no aparece como cuello inicial.
- Escalar Q5 format a 4 sin cambiar prefetch casi no mejora.
- Subir prefetch si mejora.
- RabbitMQ aparece con CPU alta.

## Posibles lineas de mejora

### Mejora chica: prefetch configurable

Para filtros stateless, `prefetch=50` o `prefetch=100` puede ser razonable.

Riesgo:

- Mas mensajes en vuelo.
- EOF/control messages requieren cuidado si hay ordenamiento o estado por cliente.

### Mejora chica: escalar consumidores calientes

Escalar solo donde RabbitMQ muestre backlog:

```text
filter_q5_format_queue
filter_usd_queue
filter_q3_queue
scatter_gather_mapper_queue
sum_q2_queue
```

Riesgo:

- Si RabbitMQ ya esta saturado, mas consumidores no mejora.
- Puede mover el cuello a la siguiente cola.

### Mejora media: reducir fanout innecesario

Problema actual:

```text
Cada transaccion se duplica hacia muchas colas aunque no todas las queries la necesiten.
```

Idea:

- Usar routing mas selectivo.
- Separar exchanges por query o routing keys.
- Evitar que Q5 y otros filtros reciban datos que descartan inmediatamente.

Riesgo:

- Cambia arquitectura.
- Hay que cuidar integracion con Q1/Q2/Q3/Q4.

### Mejora media: batching

En lugar de publicar/ackear una transaccion por mensaje, procesar lotes.

Beneficio:

- Menos overhead por mensaje.
- Menos trabajo para RabbitMQ.

Riesgo:

- Cambia protocolo interno.
- EOF y conteos esperados se vuelven mas delicados.

### Mejora para hito futuro: tolerancia a fallos

Para fault tolerance, hay tension entre:

```text
throughput alto
durabilidad
ack correcto
reprocesamiento seguro
```

Por ahora, conviene separar mediciones de performance de decisiones de durabilidad final.

## Estado de la conclusion

Con la evidencia actual:

```text
No parece que Q5 USD ni rates_service sean el cuello inicial.
El cuello aparece en las colas que reciben el fanout completo.
prefetch=1 limita bastante.
RabbitMQ tiene alta CPU y pagina mensajes a disco cuando el backlog crece.
Escalar workers sin subir prefetch no mejora casi nada.
Subir prefetch a 50 mejora de forma visible.
```

Proximo paso recomendado:

```bash
Q5_DATASET=LI-Small Q5_FORMAT_WORKERS=4 USD_WORKERS=4 PREFETCH_COUNT=50 KEEP_CONTAINERS=1 make test-q5
```

Despues de esa corrida, decidir:

- Si escala: ajustar defaults/configuracion de workers.
- Si no escala: priorizar reduccion de fanout, batching o rediseño del flujo de mensajes.
